# Mario Kart 64 fix plan

## Baseline

The 2026-09-25 Wii run completed 3,600 VIs for Mario Kart 64 at 59.53 average VI/s, but rendered only 0.86 average frames/s (64 batches, 4,140 vertices). A recent isolated Dolphin run reached the Nintendo logo, then showed `Dynarec got stuck in a loop -- stopped and returned to menu`. It did not produce `perf.log`; the five-game chain therefore did not provide a valid input comparison. These results confirm a rendering/execution failure, not its cause.

The latest matched Dolphin A/B used 1,800 VIs per run, forced dynarec, and disabled interrupt randomization. Both reached the VI limit at 0.98–0.99x speed and about 26 FPS. Both had identical totals: 14,398 exceptions, 1,347 recompiles, 98,876 batches, and 2,441,061 vertices. No-input and replay runs therefore show no measured difference in those counters. The replay trace did not establish button consumption: the first run logged four unchanged pad records; the second logged none. Both final XFB captures were solid purple. A 600-VI Super Mario 64 control also produced a purple XFB, so this capture point is not a valid visual pass/fail signal. An earlier full-frame Dolphin capture showed black followed by the Nintendo logo, without a Mario Kart title screen. Do not use the on-screen dynarec trace for causal tests; it changes behavior. Mario Party 1–3 also returned early in the earlier short triage runs.

A later raw-SD Dolphin run with the expanded stop-path instrumentation reached 1,533 VIs at 58.60 average VI/s, 25.84 average FPS, 68,983 batches, and 2,096,631 vertices. It ended before the requested 3,600 VIs and recorded `ShutdownWii: called`, but none of the newly instrumented early-stop reasons. Treat it as incomplete, not a pass or a diagnosed fault. Dolphin could not upload results to the Mac listener in this mode; the script recovered `perf.log` from `WiiSD.raw` after shutdown. The raw card retains older appended results, so compare the last complete `game:` row and its adjacent marks rather than aggregating the file.

The first Wii attempt exposed a runner bug: it wrote the selected config locally but sent only the DOL. The Wii therefore ran the SD card's old nine-game `hardware.txt` chain. That run recorded Mario Kart at 3,600 VIs, 0.7 FPS, and 64 batches, consistent with the existing 0.86-FPS baseline, but it is not the requested A/B. The runner and Wii now support per-run `--diag=` wiiload arguments instead of relying on the stale SD config; the app records the config source and loaded replay-record count, and the runner checks expected row count and HBC return.

The first matched pure-interpreter test then exposed an argv indexing bug: Wii received diagnostic arguments, but the first `--diag=` option was skipped because parsing began at `argv[1]`. The chain still ran because its option came later, masking the dropped `dynacore=pureinterp` setting. Scanning argv from slot 0, while accepting only `--diag=` entries, fixed it. The hardware checker now requires receive, parse, apply, and runtime-dispatch markers. On the fixed build, Wii ran 1,800 VIs in 48.2 seconds at 17.3 FPS with zero recompiles; its XFB shows the Mario Kart race in progress. In a concurrent Dolphin run using the same DOL and settings, the interpreter also had zero recompiles and ran at 14.5 FPS. Both tests completed; the Wii returned to Homebrew Channel. A second paired dynarec run confirmed the full marker chain and checker: Wii and Dolphin each reached 1,800 VIs at about 26.4 FPS, with 1,341 recompiles on Wii and 1,341 on Dolphin. Dynarec remains faster and renders correctly on Wii. The SD replay file is still missing, so these are no-input core comparisons.

The corrected Wii diagnostic uses one boot for two 1,800-VI runs. Both explicitly force dynarec and set `randomize_interrupt=0`; one has no replay and one replays `kart_start`. It logs how many replay records were loaded. This is diagnostic only, not a release candidate.

## Workflow

1. **Reproduce quickly in Dolphin.** Run `.dev/mario_title_triage.sh glN64_wii`. It makes a `PERF_PROF` build, then tests Mario Kart with and without the existing controller replay in separate profiles. It also tests Mario Party 1–3 with periodic A presses. Each run writes compact stats, final XFB captures, and available pad traces to `.dev/runs/`. Full Dolphin frame dumping stays off because it generated gigabytes of PNGs during the previous test.
2. **Classify the fault.** Compare no-input and replay runs. Check stop markers, VI/FPS rate, batches, vertices, exceptions, recompiles, final XFB, and pad trace. Do not treat the host VI timer as proof that the guest game advances. Verify the ROM’s CIC independently before connecting this to existing CIC-6105 findings.
3. **Make Dolphin runs finish reproducibly.** Capture the exact emulator exit/timeout status and bound each test by both wall time and VI count. Use raw-SD extraction when folder sync is stale or the game hangs, and retain only the newest run’s log slice in summaries. If the result ends without a stop-reason marker, add targeted instrumentation at the observed return boundary before changing emulator behavior.
4. **Retest in Dolphin.** Rebuild with `.dev/build_profiling.sh glN64_wii`, repeat both Mario Kart cases in separate profiles, then run the Mario Party input checks. A candidate passes only if it reaches the full 3,600-VI test without watchdog or unexplained early exit, shows the title/game advancing in captures, improves substantially on the Wii baseline (0.86 FPS / 64 batches / 4,140 vertices), and adds no new errors. Keep trace overlays disabled for performance or causality tests.
5. **Collect a hardware diagnostic.** With Homebrew Channel open, run `.dev/hardware_run.sh glN64_wii mario_kart_diag`. This A/B run is allowed before the Dolphin gate because it uses the existing diagnostic build only to collect evidence; it is not considered a fix. Check both rows, captures, and return-to-Homebrew-Channel status. After a candidate passes Dolphin, use `.dev/hardware_run.sh glN64_wii mario_kart` for the 3,600-VI final confirmation against the baseline.

## Stop conditions

If the replay changes neither Dolphin nor Wii behavior, stop adding button presses and investigate the repeatable execution/rendering path. If a Dolphin run ends before 3,600 VIs or lacks an interpretable final capture, mark it incomplete and do not promote that build to the Wii. If the watchdog fires after a code change, do not promote that build. If Dolphin passes but the Wii fails, retain the logs and XFB and investigate hardware-specific behavior before changing the fix.
